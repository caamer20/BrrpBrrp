## What BrrpBrrp is

One Go binary with an embedded web frontend and SQLite: a small community runs its own
chat and voice space — channels, threads, direct conversations, voice and screen sharing,
moderation and recovery — on a Windows machine or in a container, without a second service
to operate. The frontend is compiled into the binary; the database is one file under the
data directory.

## What 1.0 gives you

*(Draft. Each line is what the release intends to state; each must be checked against the
final candidate before this becomes the release note.)*

- **Community chat**: channels, categories, roles and delegation, pinned messages, search,
  named threads with their own reading position, mentions and notification preferences.
- **Voice and screen sharing**: a small SFU with mute, deafen, push-to-talk, room
  movement, screen sharing with its own audio, and an embedded relay for networks that
  need one.
- **Private conversations** (on by default): direct messages and groups with consent, blocking,
  requests and private evidence reporting.
- **Moderation**: reports with selected evidence, timeouts that restore exactly what an
  account held, bounded invitations, and an audit record.
- **Operator tools**: metrics, alerts to an endpoint you control, verified backups that
  are scheduled from setup on a new installation and can be copied off the host, a
  recovery health check, and a production runbook.
- **Portability**: a member's own data export, and a documented upgrade and rollback path.

## What it is not

- Not end-to-end encrypted. The operator holds the database and can relay audio.
- Not a hosted service or a multi-tenant platform: 100 accounts and 20 voice participants
  serverwide is the profile, and it is a capacity statement rather than a promise.
- Not qualified on Windows, in a container, or on a physical device by this project yet.
- Not a supported integration API. The HTTP and websocket interfaces are the bundled
  frontend's own.

The full list is [known limitations](../known-limitations.md), which ships with the release
rather than being summarised here.

## Upgrade and rollback

Upgrading from an alpha is a supported forward migration; the path, the pre-upgrade backup
and the rollback boundary are in [upgrading.md](../upgrading.md). Existing installations keep
the settings they have, including a backup interval and a feature gate set explicitly. The
shipped interval default is 12 hours; an installation that already stores a longer one is
not changed by the upgrade. Scheduled backups start switched on for a new installation
only: one that had them off still has them off, and should switch them on.
