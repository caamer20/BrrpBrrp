# 0.4.0-alpha.7 — Private message evidence and request discovery

**Checkpoint:** 27 September 2026  
**Database:** 13 · **Backup format:** 2 (unchanged — a schema 13 database is still format 2)  
**Status:** local development candidate; v1 release gates remain open

## What this release adds

Two bounded slices, both behind the existing opt-in gates, plus the follow-up
repairs review 9 asked for.

**Private message evidence.** A member can report one message from their own
accepted direct conversation. The dialog shows the exact text the server would
save, who can review it, how many accounts hold that permission, when it expires,
and what is *not* included — no history, no replies, no files, no link previews. A
message edited between the preview and the confirmation is refused and re-asked
for, so nothing is disclosed that the reporter did not read.

Evidence is reviewed through a new capability, `report.review_private`, delegated
explicitly. A community moderator's grant does not reach it and holding it grants
nothing else: the reviewer sees the submitted snapshot, not the conversation, its
history, its search or its files. Resolving a report records triage — it deletes
nothing, blocks nobody, and does not move the 90-day expiry.

**Outstanding request discovery.** The Messages entry now shows how many pending
requests are addressed to you, and opens straight onto them. The count is derived
from current durable state, so a restart, a cold start and a device that missed
events all agree. Opening the dialog does not clear it; accepting, declining,
withdrawing or blocking does. Hidden conversations stay hidden and message unread
state is untouched.

**This release adds no direct-message OS notification, push, sound or ringing.**
That is a deliberate boundary, not an oversight: the request badge plus existing
DM unread state is the whole contract for this slice. Direct conversations are
not routed into the community mention push job, whose authorization assumptions
are channel-specific.

Enable `BRRP_ENABLE_PRIVATE_CONVERSATIONS=true` on a disposable test server to
exercise either slice. **The default remains off.** Disabling the feature refuses
the routes and hides the interface; it does not erase stored evidence, which
survives until its normal expiry.

## Schema 13

Adds `private_message_reports` and a durable per-account submission counter. It
only adds tables: `message_reports` and every community report row, identifier and
expiry are untouched, as are channel-deletion semantics. It is a separate table
rather than a new kind of row in the community one because a private message has
no channel, and because one table must not carry two different disclosure rules.

## Follow-up repairs from review 9

- **CI could pass with failing browser tests.** Both browser steps reported
  `tee`'s status instead of the test process's, so a failing suite that still
  printed `[directs]` left the required job green. The steps now declare
  `shell: bash` (`-eo pipefail`), diagnostics upload with `if: always()` and
  include the original paths, and `scripts/check-browser-steps.mjs` proves the
  property by running the step bodies against a failing stub.
- **A mute on one device was invisible on the others.** A session in a direct
  conversation never re-read its mention preferences, because the only focus
  handler lived in a channel header that is not mounted there. The server now
  signals the account's own connections, and the store re-verifies on that signal,
  on reconnect and on focus.
- **Two recovery controls could not fail.** The rehearsal asserted zero restored
  push subscriptions without ever seeding one, and re-applied only half of the
  post-snapshot decisions it deliberately lost. Both now seed and reconcile.
- **An unsent draft was only tested after it had been sent.** A new rendered
  journey holds the send across an account switch with the words still unsent.
- **P8 evidence was mislabeled.** `168e89422…` and `3e08497f…` are rollback
  *archive* digests, not old binary digests; the P8 ledger carries dated
  corrections rather than edited records.

## Privacy boundary

The server operator controls the database, the media and the backups. This is not
end-to-end encryption, and an administrator outside a conversation does not gain
access to it through the application. Evidence is a record of what a person chose
to disclose, and the disclosure shown to them says so before they send it.

Pending request *introductions* are deliberately not reportable. Rejecting or
blocking erases an introduction, so there is no server-held evidence of it. A
future request-harassment feature needs recipient-only, server-verified evidence
with an explicit snapshot-before-block workflow. See
[ADR 0013](../adr/0013-private-message-evidence-and-request-discovery.md).
