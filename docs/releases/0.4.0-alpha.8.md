# 0.4.0-alpha.8 — Durable retries, revocable exports and the screen path

An alpha checkpoint, not a release. It is a working development tree, and the
"Known issues" section below says plainly what has not been established.

This checkpoint is the first tranche of the review-17 handoff. It carries the
implementation record in `planning/v1-execution-ledger-2026-10-01.md` and the
fresh verification figures below, produced against this tree.

## What this release adds

**A retry carries its own operation identity (review 17, V17-01).** A reply whose
outcome is uncertain keeps the key it was submitted under, and pressing Reply again
reuses *that* key while an earlier, different submission is still unresolved. The
association is explicit — author, account slot, destination, exact submitted words and
key — rather than "the first pending row" or a text match over the outbox, because
identical text can be an intentionally separate send and edited text can be new work.
It survives close/reopen and opted-in reload recovery, never crosses accounts, threads
or channels, clears only the acknowledged snapshot, and turns into bounded explicit
recovery when an operation ends terminally or expires instead of silently becoming a
new send.

**Export delivery is one authorization protocol (review 17, V17-02).** An export's
actual content scopes are registered with the delivery registry, and every request —
including each Range request — re-answers against the current authority, so a role or
channel-visibility withdrawal cannot fit between a stale check and admission. One scope
removed from a multi-conversation export makes that export ineligible and leaves
unrelated exports usable; group, account, session and private-feature changes stop the
appropriate transfers. Bounds, expiry, erasure, orphan cleanup and interrupted-job
handling are unchanged, and no claim is made that a copy already downloaded can be
recalled.

**Threads read like conversations (review 17, V17-03).** A thread has its own reading
position, its own unread count in the list, and a bounded window, so reading a thread
stops marking the channel and vice versa. A thread reply is a recoverable send like any
other message; a thread can outlive its subject instead of stranding its replies; the
thread is part of the send's destination and its state (locked, archived) is re-read at
the write, so a locked or archived thread refuses rather than storing. Archived threads
leave the list without disappearing, and the root keeps its identity and its link.

**Activity, moderation and export integration (review 17, V17-04).** An activity
acknowledgement covers exactly the set it names, "seen" appears only when the server
acknowledged it, an entry leads to where the thing happened, and reopening the panel
fetches rather than merely surviving. A community timeout is a community decision:
applied, audited where it commits, enforced against live accounts, lifted with exactly
the assignments it recorded, and never an installation ban. Group-message interruption
preferences are per member and per group. Page and push notices share one admission
path, and retained deduplication is bounded to 24 hours and 500 entries.

**Roles carry the effective change (review 17, commit `462e42c`).** Changing a role set
is authorized as the effective change, not as each revocation in isolation: delegated
administration cannot end up holding a capability its actor lacks, and the default role
is a floor rather than a grant that survives revocation.

**The screen path (review 17).** The screen's audio is its own publication with its own
allowance and its own lifecycle: it is announced under the offer that already carried
its m-line (a second answer for an applied description tears the call down), it is
released together with the picture, it is forwarded only for the connection that owns
it, and it is classified by the publication it was negotiated under rather than by its
codec. `screen.published` now reaches the voice store — the client's whole receive path
used to be dead code because the workspace router forwarded `voice.*` only — and
renegotiation goes through an explicit offer/answer queue so a viewer's request cannot
land between a publisher's offer and its answer. Capture is fenced to the audience that
was present when the picker opened; removing a member withdraws their screen; forced
relay now demonstrably carries a call through the embedded TURN relay, and every call
reports which path it used.

**Private evidence and reports.** The evidence queue reaches its end without looping on
exhausted sources, one row per `(source_kind, id)`, and a nonmember holding only
`audit.read` cannot learn that a private group exists. A block is a two-person fact; an
unavailable account is nobody to call.

## Schema 25

Schemas 22–25 are the export re-authorization scope, thread-root tombstones, independent
thread reading positions and group-message interruption preferences. The current schema
is **25**; backups remain format **2**, and no migration changes the backup format. The
schema-13 upgrade rehearsal reports the migrations expected beyond 13 from the registry
rather than from a hand-written list.

## Privacy boundary

- Private conversations remain **default-off** behind
  `BRRP_ENABLE_PRIVATE_CONVERSATIONS`. Nothing in this release changes that.
- A member export contains only what the account may read *now*, and its delivery is
  re-authorized per request against the same policy ordinary content uses.
- A call's participant list goes to the conversation's members; a channel's presence
  goes to whoever can read the channel.
- Screen capture is limited to the audience present when the picker opened; a removed
  member's publication stops.
- Retained notification bookkeeping is bounded and cleaned up by the same prefix the
  store uses.

## Known issues

These are the things a reader should not have to discover. None of them is a guess;
each is either unreached or unestablished.

- **A browser viewer negotiates a screen but does not decode one.** The server's view
  exchange leaves the view line `inactive`, so no frame arrives; the decode boundary is
  recorded as a skipped browser test with its measurement and the two-sided fix it
  needs (`web/e2e/voice.spec.mjs`). The negotiation, publication ownership, bounds,
  release and routing are tested; the picture is not.
- **The private features are default-off and have never been qualified on either
  required deployment.** Windows native/Tailscale and Linux Docker are unexercised.
  `docs/host-qualification.md` is written and has not been run.
- **No capacity or soak measurement exists.** The reference profile is 250 accounts,
  100 channels, a million messages, 100 clients, a two-hour peak and a 24-hour soak.
  The tooling exists and speaks the deployment's transport; the runs have not been made
  against real hardware.
- **No physical microphone, no real browser capture prompt, and no call across a
  network that blocks UDP.** The browser suite substitutes a generated stream, which
  proves the forwarding path and not the media.
- **The media architecture decision is conditional on a measurement that has not been
  made.** `docs/adr/0019-media-architecture.md` chooses to extend the embedded SFU, and
  the video-forwarding measurement at the reference allocation is still the input that
  would change it.
- **Right-to-left text is fixed in CSS and not verified by a rendered Arabic journey.**
- **No alert has been delivered to an operator's own receiver on a real deployment.**
  The mechanism is proven against a real HTTP receiver in tests.
- **No independent security or accessibility review, no physical-device observation,
  and no beta.** The accessibility sweep is automated and is not a conformance claim.
- **There is no configured Git remote in the development environment,** so no canonical
  public repository or registry identity exists yet.
