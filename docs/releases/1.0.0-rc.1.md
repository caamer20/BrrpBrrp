# 1.0.0-rc.1 — the first release candidate

A release candidate, not a release. It is the feature set intended for 1.0.0 with the two
conversation features switched on, and the "Known issues" and "Verification" sections
below say plainly what has and has not been established. Nothing here has been published.

**Schema 25, backup format 2, websocket protocol 1** — unchanged from 0.4.0-alpha.9. There
is no migration in this candidate.

## What changed since 0.4.0-alpha.9

**Both conversation features are on by default.** Restricted channels
(`BRRP_ENABLE_RESTRICTED_CHANNELS`) and consented private conversations
(`BRRP_ENABLE_PRIVATE_CONVERSATIONS`) shipped switched off through alpha.9. They are now on
for every installation that did not choose a value, and an operator withholds either by
setting it to `false`. This was the owner's decision of 6 October 2026. It was planned to
follow an independent security and privacy review; **it was made without one**, and the
guides say so wherever they describe either feature.

**A new installation starts with scheduled backups on**, every 12 hours, keeping seven
copies. The first is written within a minute of setup. Until a second destination is
configured, the recovery check reports a critical condition — "A backup kept only on this
host is not recovery" — which is deliberate. Existing installations keep the backup
settings they have.

**Sign-in throttling counts failures only.** One budget per address used to be spent by
every sign-in, password change, setup and invitation acceptance, successful or not, so the
twenty-first person behind one address was refused. Failures are now counted per address,
per address and username, and per signed-in account; a correct password spends nothing and
has a generous rate of its own. A flood of failed sign-ins can no longer close the server
to members who are already signed in. Decision D-17 in [security.md](../security.md) states
what this does and does not bound.

**For members:** a member changes their own display name and colour in Preferences. A
mention or a link inside a right-to-left message is drawn in the order it reads. Offline
members are no longer drawn too faintly to read, and links in messages are underlined.

**For operators:** a first-run checklist and a "Server details" section in Manage server →
Maintenance; `Strict-Transport-Security` on real HTTPS deployments; eight settings that
never reached the Docker container now do; the relay's TCP and TLS fallback ports are
published in Docker; the example configuration files name every key the server reads.

**For the project:** a code of conduct, a support policy, [compatibility](../compatibility.md),
[known limitations](../known-limitations.md) and an [upgrade guide](../upgrading.md).

## Upgrading

Read [upgrading.md](../upgrading.md). Three things in this candidate change behaviour
without a migration:

1. **Restricted channels and private conversations turn on** for an installation whose
   configuration sets neither switch. The native setup wizard writes neither, so a native
   installation gets both. A `.env.docker` copied from an earlier example file sets both to
   `false` and stays off. To keep them off, set
   `BRRP_ENABLE_RESTRICTED_CHANNELS=false` and `BRRP_ENABLE_PRIVATE_CONVERSATIONS=false`
   **before** upgrading.
2. **Scheduled backups** are on for new installations only. An existing installation that
   had them off still has them off; switch them on in Manage server → Maintenance.
3. **`BRRP_LOGIN_ATTEMPTS`** keeps its name and its default of 20 and now means failed
   attempts per address per five minutes. An installation that raised it to let many people
   sign in from one address no longer needs to.

## Known issues

- **No independent review.** No security, privacy or accessibility review has been run on
  this product, including on the two features this candidate switches on.
- **The last three changes have not been run.** See "Verification".
- **Nothing has been run on Windows, in Docker or on a hosted runner.** The container image
  has never been built. The CI workflow has never executed; there is no remote.
- **Acceptance runs that were specified and never built:** restricted channels exercised in
  a browser; 1,000 sends with injected faults; 100 screen-share cycles; two-device read
  state; an update between two different builds; the runtime outsider matrix; a capacity
  run; failure coverage. The race-detector sweep was not part of the last pass.
- **A shared screen's sound cannot be set apart from its sharer's voice**: one volume
  control covers both. (Until this candidate it ignored the control entirely.)
- **Under Safari's engine in the test harness, the offline page is not exercised**, because
  that pass has to block service workers to intercept requests.
- **No capacity or soak measurement, no physical microphone, no blocked-UDP call, no real
  device.** 100 accounts, 20 people in voice and 10 in a room are implementation
  boundaries, not measured capacities.

[known-limitations.md](../known-limitations.md) is the full list.

## Verification

The whole local pass was run on **6 October 2026** on commit `e2f3586`, which is this
candidate without its last three changes:

| Suite | Result |
| --- | --- |
| Frontend unit tests | 389 passed |
| Go tests | all 11 test-bearing packages passed |
| Chromium, private conversations off | 30 passed |
| Chromium, private conversations on | 45 passed |
| Firefox, voice | 14 passed |
| WebKit, core journeys | 7 passed |
| Long-thread project | 10 passed |
| Recovery, private recovery, encrypted copy (`openssl`), full disk, rollback from alpha.7, schema-13 upgrade | all passed |

Nothing failed, was skipped or did not run. The record is ledger tranches 44 and 45.

**After that pass**, three changes were made and have been checked only by the static gates
(build, vet, format, type-check and the document and packaging audits):

- both conversation features on by default — a change to two defaults in
  `internal/app/config.go`, with one test written for it. The Go and browser test harnesses
  were pinned to the old values on purpose, so the suites above still describe features
  switched off unless a test asks otherwise; restricted channels have never been exercised
  in a browser at all;
- the version, from `0.4.0-alpha.9` to `1.0.0-rc.1`;
- the listener's volume for a person now reaches the sound of that person's shared screen
  (a few lines in the voice store, with three unit tests written for it).

## The path from here

1. Run the suites again on this candidate.
2. Build and run the acceptance work listed under "Known issues".
3. Build the container image, and install on the two required hosts.
4. The independent reviews.
5. A 14-day beta with three communities, a 7-day frozen candidate, and the owner's
   publication approval.
