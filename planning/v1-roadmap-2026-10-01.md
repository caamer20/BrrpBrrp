# BrrpBrrp — the road from 0.4.0-alpha.8 to v1.0.0

**Analysed:** 1 October 2026, Pacific time.
**Source analysed:** `f8bbc74ce47fd537da848c83bc8b829e3b073eaf`, branch `codex/p9-private-reporting` — application `0.4.0-alpha.8`, schema **25**, backup format **2**.
**Contract:** [the master plan](../docs/v1-implementation-plan.md) (requirements R-01–R-14, work packages WP-01–WP-33, gates G0–G8). This roadmap does not replace it; it says what is left of it and in what order.
**Supersedes for sequencing:** the "next implementation order" in [review 17](completion-review-17-and-v1-next-steps-2026-10-01.md), whose two P1 findings are already repaired at this commit.
**Companion:** [the goal prompt for the next agent](kickoff-v1-goal-prompt-2026-10-02.md), rewritten on 2 October after the session working toward v1 was ended mid-change.

---

## 1. Bottom line

1. **The product is mostly built; the release is mostly unproven.** Every v1 feature family in the plan now has an implementation — roles and restricted channels, consented DMs, groups, blocking, named threads, activity and notification preferences, moderation and timeouts, member export, private calls, screen sharing, verified backups, alerts. The local suites are green at this commit (I re-ran them; §2.2). **No release gate G0–G8 has passed**, because every gate needs something a development laptop cannot supply: a second machine, a real network, a physical device, an independent reviewer, or elapsed days.
2. **The critical path has moved from code to people, machines and the calendar.** After a short engineering close-out, the remaining work is qualification on two real hosts, an independent security and accessibility review, a 14-day beta with three communities and a 7-day frozen-candidate observation. Those 21 observation days cannot be compressed by writing code faster.
3. **The single largest risk today is not a defect — it is that the whole project exists in one place.** There is no Git remote. `main` is 185 commits behind the working branch. The newest media fix is uncommitted in the main checkout. One disk failure loses the project. Fixing this takes an hour and is step one.
4. **Defect discovery has not converged.** Reviews 12–17 each found 5–12 new findings, reproduced P1 defects among them every time, almost all in code written days earlier. A deliberate hardening pass has to precede outside review and beta, or the beta will spend its 14-day clock on resets.
5. **My estimate:** about **75–125 focused engineer-days** of the plan's work remain, of which only **20–35** are code an agent can write locally. From the day the owner inputs in §7 exist, the earliest honest v1.0.0 is **about 8 weeks** away; **10–14 weeks** is the realistic range with one severity reset and normal reviewer/pilot scheduling. These are my judgments from the plan's own package estimates and the observed pace, not measurements.

## 5. The roadmap

Phases A–C are agent work and can start today. Phase D is owner work and **must start today in parallel**, because Phases E–I cannot begin without it. Each phase ends in a checkpoint with recorded evidence; none of them is permission to stop.

### Phase A — Secure and reconcile the work (hours)

1. Finish and land the interrupted screen-view fix (ENG-01) with its journey un-skipped.
2. Push everything to a private remote (PUB-01). Fast-forward `main` (PUB-02).
3. Fix the clean-clone break, format drift and module tidiness and add their gates (HRD-01–03). Kill leaked rehearsal servers and fix the teardown (HRD-09).
4. Diagnose the intermittent voice join (HRD-12) while its trace is fresh.
5. Correct the stale status documents (HRD-11) so one file tells the truth about what exists.

**Exit:** a fresh clone on another machine passes `make check`; the voice project passes twenty consecutive runs; the project survives the loss of this laptop.

### Phase B — Engineering close-out of M3 and M4 → `0.4.0-alpha.9` (≈ 12–20 engineer-days)

Order by risk:

1. **Media correctness:** ENG-02 feedback path with a late-join journey that decodes frames; ENG-03 presets and bounds; ENG-05 codec decision with a recorded ADR 0019 amendment; ENG-04 viewer controls; ENG-06 output device and the documented recovery path.
2. **Resilience:** ENG-11 reconnect policy; ENG-12 protocol handshake and update-required state; ENG-13 quota and disk guard.
3. **Everyday UX:** ENG-08 formatting (or descope by decision), ENG-09 profile, ENG-10 navigation.
4. **Operations code:** ENG-14 metrics and an external probe; ENG-15 encrypted-copy procedure.
5. ENG-07 external TURN and IPv6 policy — implement or record the descope.

**Exit:** every ENG row is closed or has an owner-approved descope recorded through the plan's change rule (§15.2); both browser modes green with no skipped test; `alpha.9` packaged from a clean commit and consumed as extracted bytes.

### Phase C — Hardening → feature freeze, `1.0.0-beta.1` (≈ 10–15 engineer-days)

1. HRD-06 generated negative matrix; HRD-07 acceptance matrix file; HRD-10 rendered proofs.
2. HRD-05 Firefox and WebKit projects for the core journeys; HRD-04 a race job that fits a hosted runner.
3. HRD-08 convergence passes until a round finds no P1.
4. **Flip the two feature gates to default-on** (OD-6) once G1/G2's interim review allows it. The beta must exercise the configuration v1 will ship; a product whose headline features are off by default has not been beta-tested.
5. First fully green hosted CI run, including the Docker image build and its runtime check (needs PUB-01/03).
6. Freeze features. Cut `1.0.0-beta.1` with signed checksums and provenance.

**Exit — the engineering candidate:** all local T-scenarios pass against identified artifacts; hosted CI is green on three operating systems; the image exists with a digest; no known P1.

### Phase D — Owner track (starts day 0, runs in parallel)

In lead-time order: signing certificate (PUB-06) → repository and security intake (PUB-01/04) → both hosts reachable (QUAL-01/02 prerequisites) → book the independent security reviewer and the accessibility tester (QUAL-08/09) → recruit three pilot communities (QUAL-11) → devices for QUAL-07 → name the alternate operator (PUB-09) → record the G0 decisions (§6).

**Exit — G0:** every decision in §6 recorded with a date; every later phase has a named machine and a named person.

### Phase E — Host, media and capacity qualification → G4, G5 (≈ 20–30 engineer-days, 2–3 weeks elapsed)

Run `docs/host-qualification.md` on both hosts with the `beta.1` bytes: QUAL-01–07. Two 24-hour soaks and the two-hour peaks set the floor on elapsed time. Every failure becomes a fix, a new beta build and a re-run of the affected rows — budget for at least two such loops.

**Exit:** the both-deployment table in plan §12.2 has a dated pass in every cell; RPO/RTO measured; the capacity profile either passes or is replaced by a smaller one the owner has approved and the run has confirmed.

### Phase F — Independent review → entry to beta (1–2 weeks elapsed, overlaps E)

QUAL-08 security/privacy, QUAL-09 accessibility, QUAL-10 non-author rehearsals. Remediate; no unresolved critical or high finding.

### Phase G — Beta → G6 (14 consecutive days, plus recruiting)

Three communities, both hosts, desktop and phone. Daily record of build identity, incidents, alerts and backup status. A Severity 0/1 finding restarts the affected deployment's 14 days after the fix (plan §14.3).

### Phase H — Release candidate → G7 (7 consecutive days)

Freeze source, dependencies, schema, protocol, defaults and artifacts as `1.0.0-rc.N`. One clean independent recovery and one rollback rehearsal against the candidate. Any executable, dependency, schema or protocol change is a new candidate and a new seven days.

### Phase I — v1.0.0 → G8

Explicit publication approval. Final stamped and signed artifacts verified as the bytes people will download (the plan forbids relabeling an RC binary). Staged rollout from pilots to early adopters. Day-7 and day-30 reviews.

## 8. Risks

| Risk | Why it is live now | Mitigation |
| --- | --- | --- |
| Total loss of the work | One machine, no remote, uncommitted fixes | Phase A, today |
| The beta spends its clock on resets | Reviews keep finding P1s in new code; 50% growth in five days | Phase C convergence passes and the generated negative matrix before any outside exposure |
| Screen sharing fails outside the lab | No feedback path, H.264 only, no bitrate bound, never seen on a real network | ENG-02/03/05 first in Phase B; QUAL-03 early in Phase E |
| Hosted CI is red for days | Never run; one known clean-clone break; a race job longer than the runner allows; Windows and Linux paths never executed | HRD-01/04 before the first push; treat the first hosted run as a work item, not a formality |
| The Windows path hides the most surprises | Installer, service, ACLs, tray and updater have only ever been cross-compiled | Run QUAL-01 first in Phase E, with the developer watching |
| Capacity target fails on four cores | Measurements so far are loopback on sixteen cores | OD-2 fallback agreed in advance |
| Owner inputs arrive late | Everything after `beta.1` waits on them | Phase D starts on day 0; §7 is ordered by lead time |
| One-person project at release | RK-10 in the plan | PUB-09 before beta, or publish the limitation honestly |
| Concurrent agents overwrite each other | Several tools have shared one checkout and stash stack | One worktree and branch per agent; merges through `main` |

## 9. Versions and checkpoints

`0.4.0-alpha.9` (Phase B exit) → `1.0.0-beta.N` (feature freeze; hosts, reviews and beta run on these bytes) → `1.0.0-rc.N` (frozen candidate) → `1.0.0`. Never overwrite a published identity; every build after a fix is a new N. Schema and backup format continue independently of the version.

Each checkpoint records: source commit and clean state, toolchain, executable and archive hashes, image digest, the commands run with exit status and counts, what the result proves, and — required — what it does not.
